# Internal runtime jobs remain invisible at the prompt

The public `v0.1.1` bundle prints a Zsh job announcement such as `[4] 835302` before its first prompt. The line exposes an internal implementation detail and makes clean shell startup depend on the caller's existing job count.

The failure reproduces by installing `v0.1.1`, running `wsh run` from an interactive Zsh, and capturing the PTY transcript. The same line appears when `tests/runtime-pty.zsh` sources the integration under an interactive bundled Zsh with `MONITOR` enabled. The measured release is source commit `e62e19fe1cf8b10d28b703e2670b6478e540f38d`, manifest `9ec9ecf5226a39220b96f8a3e1522229b5ffea0ebc7bbd3909465500dd6e373e`, and bundled Zsh 5.9.2.

The cheapest counterfactual was to disable `MONITOR` only within `_wsh_runtime_start` before creating the coprocess. It suppressed the announcement and restored the caller's option, but `/proc` showed that the runtime then shared the interactive shell's process group. That result was rejected because terminal-generated signals at the prompt could reach the internal service.

The second counterfactual keeps the locally unmonitored coprocess creation and makes `wsh-runtime serve` establish its own process group before it loads the theme or reports ready. The change passes when the PTY transcript contains no line matching `[N] PID`, the runtime process-group ID equals its PID and differs from the shell's process group, the runtime survives a real Ctrl-C at the prompt, the Git-aware prompt renders, shell-exit cleanup passes, and `MONITOR` remains enabled after startup. A failure of this second implementation triggers a new ownership design rather than another local patch.

The fix also retains the existing cold-start gates from the installed-startup experiment: complete managed startup may add at most 5.0 ms at p90 and 8.0 ms at maximum over raw bundled Zsh, and the manager may add at most 1.0 ms at p90 over the direct complete path. The public release and changed development bundle are measured with the same first-editable harness on the same host; the comparison is a regression check rather than a claim that the one-line option change improves latency.

The first safe-implementation measurement on CPU 0 passed both complete-startup gates but measured 1.172 ms of manager contribution at p90, above the 1.0 ms gate. Host load was 4.47 with another process consuming 128 percent CPU, and the raw Zsh p90 was 1.248 ms slower than the preceding run. The failed samples remain retained. One confirmation pins both the corrected bundle and published control to CPU 31 and reverses their measurement order by running the corrected bundle first. The result is accepted only if all three unchanged gates pass; a second miss rejects the implementation pending a new design or benchmark hypothesis.
