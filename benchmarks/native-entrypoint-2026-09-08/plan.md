# Native entrypoint versus installation-owned launcher

The question is whether moving Wsh startup into the already patched Zsh removes code and compatibility hazards compared with a small launcher that uses an installation-owned default. The current source is `a3d6c937f5219a0158234c54d4ba7099ba743a05`; existing uncommitted documentation changes are outside the implementation. This is an unsigned local prototype, not a release or a change to account shells.

The reproduced baseline is the retained [login failure](../login-recovery-2026-09-06/report.md): user activation state can prevent Zsh from starting, and the old manager rejected native shell arguments. Current recovery can switch to Bash. Startup wrappers also manually source four user files and preserve ZDOTDIR and RCS across them. The cheapest counterfactual is a separate small Rust launcher forwarding native shell arguments to an adjacent complete Zsh installation, without consulting user state. It retains existing startup wrappers. The native candidate resolves its own installation and invokes Wsh setup around Zsh's existing startup-file reader. Rust management, runtime, providers, rendering, and editor components remain unchanged.

Build controls from the same locked upstream archive with the two existing patches, compiler, configure options, and modules. Add only the entrypoint patch for the candidate. Keep optional services and presentation identical. Retain generated adapters, source patch, build commands, binary and fixture hashes, results, and failed attempts. Prototype assembly must not masquerade as a verified immutable bundle; manifests for adapted installations must describe their actual bytes before manager-driven tests.

Before timing, require fresh-home and absent/corrupt/unreadable user-state startup using Zsh semantics; native login argv[0], -c, -l, -f, scripts, exact argument bytes and exit status; redirected ZDOTDIR and startup order; existing configuration, editing, foreground job control, native terminal reporting, and profiling regressions where the prototype supports their entrypoints. Include startup files using native top-level context and option changes, and installation relocation. Exercise the native patch with the upstream suite. Management-mediated tests supplement rather than replace direct-entrypoint checks.

Compare 50 alternating pairs of installation-owned launcher and native starts in each of existing-prompt and Wsh-theme modes, on the same CPU and fixture, without overlapping builds or checks. End timing at native OSC 133 B after editor initialization; retain every sample. Fix the native regression threshold at paired p95 no greater than 3 ms. Measure empty-command exec overhead separately only if needed to explain readiness; do not infer it from unrelated historical prompt timings.

Count added native code, retained adapter code, and specifically removable wrapper code. Manager code still used by update, doctor, profile, and structured foreground commands does not count as deleted. A native recommendation requires passing behavior plus an identified reduction in duplicated startup semantics; speed alone is insufficient. Tracking latest upstream already requires maintenance, so compare only additional patch conflicts and changed semantics, not the entire existing upstream workload.

Allow at most two interventions at a failing correctness or timing gate before auditing the premise. Bound each hypothesis to two hours; retain blockers and move to another independent check instead of broadening the prototype into an installer migration, daemon, or shell rewrite. Host prototype results can establish a direction; release acceptance still requires canonical portability, reproducibility, and update/migration gates.
