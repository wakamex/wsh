# Trace overhead and retained memory receive fixed phase-one gates

The phase-one release gates already bound normal prompt latency, process count, optional-lock behavior, repainting, and semantics, but tracing overhead and retained memory were recorded without pass thresholds. This experiment fixes both gates before the accepted run. Tracing may add at most 3.0 ms to runtime-ready p90 and 0.5 ms to refresh p90. The combined Zsh and runtime path may add at most 4,096 KiB of retained PSS at p90 and 5,120 KiB at maximum over raw bundled Zsh.

The refresh threshold comes from the feature's purpose and two earlier accepted measurements. Tracing must remain useful during performance diagnosis without consuming a material fraction of the 7.1 ms settled-latency budget. The largest trace-minus-untraced updated-prompt p90 differences were 0.345 ms in the current fixed run and 0.399 ms in the preceding accepted reproduction. A 0.5 ms ceiling covers those observations while limiting tracing to 7 percent of the normal settled budget.

The earlier PTY statistic labeled first-editable measures the prompt returned immediately after a command while asynchronous collection continues; it does not measure trace-file creation or runtime readiness. The corrected paired harness exposed that distinction: a nine-pair instrumentation pilot measured 1.731-2.046 ms of one-time traced runtime-ready overhead. The separately fixed 3.0 ms p90 gate bounds that startup cost with roughly 1 ms of margin. This is a benchmark-design correction to the measured quantity, not a relaxation of the unchanged 0.5 ms refresh gate.

The retained-memory gate applies per interactive session because phase one starts one runtime for each Zsh process. A three-pair instrumentation pilot after five prompts measured 1,993-2,003 KiB of added PSS. The 4 MiB p90 gate allows roughly twice that pilot value, and the 5 MiB maximum catches isolated excessive retention without making page-accounting noise a release failure. Twenty panes at the p90 ceiling would add 80 MiB. This gate covers retained idle memory, not transient Git child memory while a request is running.

## Accepted trace workload

The initial order-reversed PTY comparison was rejected as a tracing-overhead measurement after its traced-first block made every clean scan about 5 ms slower while later states normalized. Repeating traced wsh alone reproduced the state-order effect. Separate target runs could not distinguish trace cost from cold repository and filesystem state.

The corrected comparison pairs fresh untraced and traced runtimes for every sample and alternates pair order. Each runtime reaches ready, warms both sides of the requested state transition, returns to the preparation state, and then processes the same real Git transition in the pinned 1,000-file fixture. Warming both sides is required because the first clean scan hashes tracked content while the dirty preparation scan does not; a one-sided warmup produced a mid-run 9-to-4 ms step in both traced and untraced Git work and was rejected. The run contains 20 pairs for clean, tracked-dirty, and untracked states. The ready gate uses nearest-rank p90 over all 60 process pairs; the refresh gate uses the largest state-level nearest-rank p90. This isolates trace-file creation and event recording while exercising the real parser, provider, renderer, and trace implementation. The separate PTY benchmark continues to cover shell integration, semantics, process count, optional locks, and repaint behavior, while the trace file's bound and privacy remain correctness tests.

## Accepted memory workload

The accepted retained-memory comparison uses 20 paired fresh sessions of raw bundled Zsh and bundled Zsh plus the runtime. Pair order alternates. Both run in the same committed 1,000-file repository fixture. Each process reaches an editable prompt, runs 20 prompt cycles, waits 250 ms without input, and then reads `Pss` from Linux `/proc/PID/smaps_rollup`. The wsh observation is the sum of the Zsh and runtime PSS; added PSS subtracts the paired raw-Zsh PSS. The p90 is nearest-rank over the 20 added values, matching the latency benchmark's percentile rule.

The accepted run must use a clean glibc 2.28 development bundle built after these thresholds are committed. It records the source revision, bundle manifest, all measured file digests, benchmark and runner digests where applicable, host, commands, raw measurements, generated summaries, and admission results. A failure does not change these thresholds. It starts a measured attribution experiment with one causal intervention and a two-attempt limit.
