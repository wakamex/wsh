# The public installer must reach an editable prompt within 5 seconds at p90

The first official release makes the previously deferred measurement possible: how long does the documented public command take from its first HTTPS request until the installed shell presents an editable prompt? The accepted path must work from fresh isolated state on the current Fedora host and inside the pinned glibc 2.28 Rocky 8.10 environment. Its total p90 must be at most 5 seconds in each environment, its post-install first-prompt p90 must be at most 50 ms, and every measured installation must select the exact `v0.1.0` bundle from source commit `e253573211e0d6a9d2943f943ff04ae1d21f6dd9`.

Each environment receives one unmeasured correctness run followed by 10 measured runs. Every run creates fresh home, binary, libexec, install, and activation directories. Timing begins immediately before downloading the release-specific bootstrap from its immutable GitHub Release URL. The harness records bootstrap-fetch, bootstrap-execution, first-prompt, and complete elapsed milliseconds separately. Bootstrap execution includes the four real GitHub HTTPS asset downloads, native-tool digest checks, offline GitHub Actions provenance verification, archive validation and extraction, complete payload hashing, smoke tests, and atomic activation. The final interval launches the installed `wsh` under a PTY and ends when its first editable `% ` or `# ` prompt is observed.

The environment process is already running before measurement, so container startup is excluded from the glibc 2.28 result. Network conditions are recorded but not controlled; the result describes GitHub delivery observed from this host rather than a universal download latency. A failure to download, verify, activate, identify the exact release, or reach a prompt fails the experiment rather than becoming a latency sample. The implementation attempt limit is one because this measures the already published immutable release rather than tuning an intervention.
