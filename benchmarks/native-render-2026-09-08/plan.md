# Compare a complete C runtime with unchanged themes and helper ownership

Start from `53f020a` and the passing stage-5 C collector. The Rust runtime still owns TOML decoding, theme validation, rendering, request parsing, generation publication and trace output; its temporary collector bridge adds 160 lines. The hypothesis is that a complete C helper can remove that bridge and Rust runtime dependencies while preserving the existing user definitions and per-shell process architecture. This experiment does not yet move asynchronous work into Zsh.

First compare theme parsing and validation, then rendering, then the complete protocol/lifecycle path in independent slices. Keep schema version 1 and all four shipped TOML themes. Use maintained parser source with pinned provenance and authoritative parser suites rather than implementing TOML or JSON tokenization in Wsh. Count vendored source, system dependencies, Wsh-owned patches and temporary test interfaces separately. Test semantic parity against the actual Rust parser and renderer, not copied expected output alone. Do not change the theme format in this language-port experiment.

The initial TOML candidate is tomlc17 `64a063b8636a4b48d142f978270f5e53e605e240`. The actual Rust baseline accepts `duration.threshold-ms` through `18446744073709551615`; the candidate's signed-only decoder rejects values above `9223372036854775807`. Its unmodified scanner also rejects a valid 63-digit binary integer, and strict UBSan stops at the pool allocator's null-pointer offset expression before parsing ordinary input. Before adopting it, evaluate local, bounded fixes for these reproduced cases and run the pinned authoritative TOML suite. If preserving the existing definitions requires disproportionate parser maintenance, retain the comparison and audit the parser choice rather than narrowing the public contract silently. Allow two interventions or two hours per failing parser gate before requiring a new hypothesis.

For JSON, evaluate yyjson `6447536015f3d600f3d65323b10976103b337ca7` because its actual API preserves u64 and i64. The existing system Jansson reader represents integers as signed 64-bit; using it for the runtime protocol would narrow already tested request IDs and generations. Require strict UTF-8, explicit type/range checks, duplicate-field behavior matching the existing request parser, the 64 KiB input-line bound and bounded pending work. Do not add a new public interface or a second helper. Keep a possible later consolidation of the native saved-profile reader separate from this experiment.

Theme correctness covers shipped and generated definitions, required and unknown fields, duplicate keys and components, table/array forms, numeric boundaries, literal byte/character limits, malformed encodings, control characters, long strings, color/segment consistency and executable-looking literals. Rendering compares exact left/right prompt bytes across environment values, Unicode and raw path bytes, branch/tag/operation/dirty/divergence states, duration thresholds, privilege/exit status, repeated snapshots and transient reset. If emitted terminal sequences change, validate them against the real terminal parser before accepting the change. Prefer preserving exact output in this slice.

Run strict warnings, ASan/UBSan, deterministic parser mutations, existing real-Git and native-installation contracts, runtime crash/parent-death/EOF/cancellation tests and trace recovery before timing. Preserve one asynchronous Git process, optional-lock suppression, cancellation and complete final-generation snapshots. Reuse the stage-5 50-pair collection and native-startup workloads with at most +3 ms paired p95 regression, the existing retained-PSS bounds of 4,096 KiB p90 and 5,120 KiB maximum, and trace-overhead bounds of 3 ms readiness and 0.5 ms refresh p90. Add 1,000 alternating in-process theme-parse and renderer samples per shipped theme, with paired p95 regression at most +0.5 ms and +0.05 ms respectively. Report code, executable and dynamic-library size, CPU and memory as well as latency. Timing runs remain sequential and use matching instrumentation.

Allow two interventions or four hours per failing Wsh correctness/performance gate before a premise audit. Preserve failed inputs and successful evidence, commit independently, and retain any decision-dependent implementation as an opt-in prototype. No release, push, live account change, theme-directory backend, arbitrary executable theme support or cross-shell service is part of this stage.

The parser microbenchmark retains 1,000 alternating pairs after one warmup per variant and shipped theme. Both variants measure parse, validation and destruction of a previously read source string with monotonic clocks; process startup and pipe exchanges stay outside the measured spans. An empty-clock workload uses the same sample count to quantify instrumentation cost separately. Run both processes on CPU 0, preserve each raw duration, and calculate the predeclared +0.5 ms paired p95 gate without subtracting instrumentation overhead.
