# Native tool comparison

The question is whether a native tool interface can remove the standalone manager boundary while preserving ordinary Zsh arguments and useful diagnostics. The baseline is commit c5066ce and the accepted native-entrypoint experiment at ec7e9e9. The smallest candidate adds an explicit first-argument dispatcher to that native binary. Compiled version identity is implemented before doctor; neither tool requires user activation state.

Version identity is compiled into the executable, so reading version information cannot fail because mutable installed metadata is absent or malformed. It describes the build, not a verification of installed resources. Doctor will test installed integration separately. This avoids adding a JSON or cryptographic parser solely to recover executable identity.

Before implementation, the version gate is fixed: preserve script-name and argument bytes/status against the same upstream binary; do not read user startup for tool dispatch; handle missing HOME, corrupt activation state, non-UTF-8 paths/arguments, extra arguments, and ambiguous names deterministically. A standalone dispatcher harness receives compiler warnings, ASan, UBSan, and 10,000 deterministic arbitrary argument cases. Compare 50 alternating process-exit latency pairs with upstream `--version`; allow +3 ms paired p95. This measures a complete short command, not editor startup. Keep all samples. The first version hypothesis has at most two interventions or two hours before a premise audit.

Doctor's baseline is the current Rust report and its existing plugin and real OMZ fixtures. Preserve the ten-second bound and isolation from configuration output. Test exact, modified, disabled, absent and inconsistent ownership, prompt overlap, early exit, hanging startup, and unchanged user files before comparing 50 paired invocations. The declared latency gate is +3 ms paired p95 relative to the existing doctor on the same native installation. The first doctor hypothesis has at most two interventions or four hours before a premise audit. Parser or child-lifecycle changes require focused sanitizer and hostile-input tests.

Build records must retain the source revision, copied source identities, generated build identity, compiler command and version, executable hashes, effective environment, logs, commands, raw results and summaries. Production adoption of startup and package layout is a separate stage.
