# Locked native startup build

The selected native entrypoint must be buildable from the repository's verified source inputs instead of a preserved scratch tree. The baseline is native tools and foreground startup at 4dafee9, using the retained native-entrypoint prototype. The observed costs are the prototype-only builder, manual startup redirection still installed by the legacy bundle path, repeated interpreted resource-path setup, and missing relocation setup under `-f`.

The candidate adds a separate native source lock and normal native build entrypoint while reusing the existing pinned Zsh builder and payload assembly. The currently published per-user bundle contract remains available until the migration stage. Native installations contain a direct executable and thin before/after setup, with no redirecting `.zshenv`/`.zprofile`/`.zshrc`/`.zlogin`, no ZDOTDIR/RCS restoration state machine, and no legacy foreground callback. Native resource paths are initialized before optional integration, including `-f`; user startup remains owned by Zsh. Existing public environment knobs are preserved. This is one native-startup integration change; package layout and runtime language/process changes remain separate.

Before implementation, correctness gates are fixed: upstream Zsh suite; native argv and startup context/status; global and user startup order, login/logout, ZDOTDIR redirection, RCS/GLOBAL_RCS, nested shells and no-rcs behavior; absent/corrupt/unreadable activation state; relocated executable/resources and no module fallback; early module loading; no optional integration/runtime; real OMZ coexistence; plugin and theme ownership; and the accepted foreground byte/job-control/terminal contract. Verify source-input tampering is rejected and a build output cannot be reused across a changed native identity. Native C changes receive the established scoped ASan/UBSan checks.

After correctness, compare 50 alternating first-editable pairs per prompt mode with the accepted prototype, trace off, matching resources, compiler flags, user configuration and global startup policy. Require +3 ms paired p95 or better and preserve all samples. At most two interventions or four hours are allowed on the initial hypothesis before a premise audit. Retain exact build identities, source lock, source snapshots, commands, fixtures and logs. System-account installation is deferred to the next stage's real RPM/VM tests.

## Startup ownership audit

The first native assembly dropped the prototype's final theme unexport; a login fixture proved that `.zlogin` could leak WSH_THEME into child environments. Native cleanup now uses Zsh's parameter/export operations after all startup files. That fix passes the scalar export and real nested-Zsh ownership checks.

A genuinely empty HOME then exposed another missed distribution boundary: upstream `zsh/newuser` loaded its setup wizard from the configured build prefix and withheld the first prompt. The previous fixtures all supplied at least one startup file. The revised hypothesis is that successfully loaded Wsh defaults should suppress the automatic upstream new-user wizard; manual invocation and missing-integration fallback should retain upstream behavior. Add one conditional at the existing newuser load boundary, preserve the failed transcript, and test empty-home prompt readiness without creating startup files. Keep the existing correctness and +3 ms gates. Allow at most two interventions or two hours for this revised startup-ownership hypothesis. No new setup subsystem or automatic configuration writing is proposed.
