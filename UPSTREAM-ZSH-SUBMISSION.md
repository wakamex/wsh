# Submitting fixes to upstream Zsh

This guide describes how Wsh sends confirmed Zsh fixes upstream: where patches go, how the zsh-workers list formats and reviews them, and how to pace several fixes. [UPSTREAM-ZSH-BUGS.md](UPSTREAM-ZSH-BUGS.md) records the defects themselves, their status and the submission order.

The project's own rules are in `Etc/zsh-development-guide` and `Etc/FAQ.yo` in the [Zsh source](https://github.com/zsh-users/zsh). The observed conventions below come from the 290 patch posts and 657 replies on zsh-workers in 2026 through early October, and from upstream `master` history over the preceding year.

## Channel

Patches and bug reports go to `zsh-workers@zsh.org` as plain-text email. Over the year to October 2026, 345 of the 460 commits on `master` came from list posts, 81 were committed by maintainers without a post, and 22 came from pull requests on the GitHub mirror, mostly completion fixes. The list is the primary channel for shell changes.

Subscribing is optional. The FAQ invites non-subscribers to ask for replies to be sent directly, and recent posts end with lines such as "PS I'm not subscribed; please Cc me." A zsh-workers subscription also delivers zsh-users and zsh-announce. To subscribe, send any email to `zsh-workers-subscribe@zsh.org` from the posting address and confirm the reply from the list's [Sympa](https://www.sympa.community/) server; `zsh-workers-unsubscribe@zsh.org` reverses it. A Gmail filter for the search `list:zsh-workers.zsh.org -to:me` that skips the inbox keeps list traffic out of the inbox while replies addressed or copied to the sender still arrive there.

Every post appears in the public [archive](https://www.zsh.org/mla/), for example `https://www.zsh.org/mla/workers/2026/`. Each message shows its `X-Seq` number, also available as `https://zsh.org/workers/NNNNN`. Maintainers cite that number in the commit subject (`55140: fix pointer math in join_sub`) and add the `ChangeLog` entry themselves, so contributors include neither.

## Maintainers

Five people committed almost all of `master` in the year to October 2026: dana (150 commits), Mikael Magnusson (131), Oliver Kiddle (90), Bart Schaefer (64) and Jun-ichi Takimoto (24). Those 460 commits came from 44 authors. With this few reviewers, a response can take days or weeks. After about two weeks without one, a short reply to the original thread asking whether anyone has had a chance to look is normal.

## Patch content

The development guide asks for:

- unified or context diffs with paths relative to the top of the source tree; Git-style diffs are acceptable
- one bug fix or feature per message, in the smallest logical unit, without splitting needlessly
- a statement of the Zsh version the patch is for and of any patches it depends on
- a patch that has been tested and applies cleanly
- a subject starting with `PATCH:`, `[PATCH]` or `[PATCH n/m]`

In 2026, 129 patch subjects used `[PATCH]` and 114 used `PATCH:`. Revised patches use `PATCHv2:` or `[PATCH v2]` in the same thread.

Recent bug-fix posts follow a consistent shape: the affected version, such as "Against master (26ba0e39b); also present in 5.9.1 and 5.9.2", a minimal reproducer using `zsh -f` or `zsh -fc`, the expected and observed output, the cause named by function, and a sentence on what the patch changes and which tests it adds. The tone is short and casual. Claims a reviewer cannot check, such as private test counts or anecdotes, invite questions; analytic explanations and reproducers do not.

Reviewers push back on structure: one patch was split into functional and formatting parts at a reviewer's request, and another was reposted so that it no longer depended on an unmerged patch. Fix only the defect, and keep cleanups out.

Add a regression to the relevant `Test/*.ztst` script when it is feasible. A non-interactive case often is: the stale history lock fix is covered by `fc -R` on a file with an aged lock, without a terminal or real waiting. Run the case against unpatched `master` to show that it fails.

## Message format

Of the 290 patch posts in 2026, 273 carried the diff inline in the message body. 146 were generated by `git format-patch`, recognizable by the `-- ` signature followed by the Git version, and 52 of those put notes for reviewers between the `---` line and the file summary, where `git am` ignores them. None used a scissors line. 48 posts contained prose lines longer than 100 characters, so wrapping prose at about 72 columns is the norm without being enforced. Grouping 2026's 397 diff-carrying posts into 300 patches and counting each patch's final version, excluding the most recent three weeks, 218 of 245 patches with wrapped prose and 31 of 38 with unwrapped prose were merged, most of the latter by one contributor. No reply objected to line length.

Wsh submissions therefore use this layout, generated by `git format-patch` against current `master`:

1. Headers: the author as `Mihai Cosma <mcosma@gmail.com>` and a `[PATCH]` subject that names the area and effect.
2. The commit message: a short description of the cause and the change, wrapped at 72 columns, since it becomes the permanent commit message.
3. The `---` line, followed by reviewer notes, one line per paragraph so that they reflow on narrow screens: the version line, the impact, the reproducer with expected and observed output, test and platform results, and any related fix that will follow separately.
4. The file summary and diff, unchanged from `git format-patch`.

Check the result with `git am` on a clean `master` checkout: the commit must apply, carry the intended author and contain none of the reviewer notes.

## Testing before sending

Build `master` with the patch and run `make check`. Run it in a terminal or a pseudo-terminal. Since upstream commit `41ba309de`, interactive tests in five scripts print prompt bytes to stderr when the suite has no controlling terminal; the [bug record](UPSTREAM-ZSH-BUGS.md#interactive-tests-fail-without-a-controlling-terminal) describes this. Under a terminal the complete suite passes, so a report of failures without one would only distract from the patch.

Verify every behavioral claim in the message against three builds: the latest release, unpatched `master` and patched `master`. Cover each path the defect reaches, not only the reported symptom; the history lock fix affected live locks as well as stale ones, which changed how the message described its impact. Find the releases that contain the commit introducing the defect with `git tag --contains COMMIT` and state them, since a regression in a release is more urgent than one only on `master`. Say what the new test does not cover.

Before sending, a sealed review from the maintainers' perspective, given only the patch, the message, the affected upstream files, the commit that introduced the defect and the development guide, catches overstated claims and missing tests. [AOP](https://pypi.org/project/agent-orchestration-process/) runs such a review with `--profile sealed --no-web`. Review the exact message that will be sent, after every revision of its text, since a review of an earlier draft does not cover later wording. Each open-ended round tends to produce new optional wording, so once the findings are only optional, ask the final round to report only factual errors, `git am` or test failures, and likely grounds for rejection. A sealed reviewer cannot build or run anything and may be wrong about the local setup, so verify each of its claims against a real build or the actual configuration before acting on it.

Finally, apply the message with `git am` on a clean `master` checkout and run `git send-email --dry-run` to confirm the sender, recipient and subject.

## Several fixes

Patch series are common and are merged whole. Mikael Magnusson's six-part series (54710 to 54715) and an outside contributor's four-part documentation series (54868 to 54871, merged the day it was posted) are examples. Philippe Altherr, also outside the committer group, kept about six unrelated patches open at once (55020 to 55026 and 55036), and all were merged over the following weeks. No reply in 2026 objected to the number of patches a contributor had open.

Large batches from new contributors can still go unanswered: a five-part crash-fix series from a first-time poster (55170) had no replies after eleven days. Wsh's fixes are independent of each other, so each goes out as its own message, starting with the most damaging defect and following [the submission order](UPSTREAM-ZSH-BUGS.md#submission-order). A fix that a previous message announced waits until that thread receives a response.

## Design proposals

Keep a fix message about the fix. A redesign proposed in the same message invites a side discussion that can delay an otherwise uncontroversial patch.

Raise design ideas in their own thread after the related fix is committed or reviewed. In 2026, such threads used question-shaped subjects ("should we use PCRE2_MATCH_INVALID_UTF ?", "Shouldn't readonly (-r) prevent type changes?"), `[RFC]` or `RFC PATCH:` prefixes, `PoC:` for an exploratory implementation, and topic tags such as `[Language Design]`. Lead with the consequence for users, then the proposal and the risks already considered, and offer to write the patch.

When a side topic grows inside a patch thread, reply briefly and move it to a new thread, or rename the subject to `New topic (was: old subject)`, as six 2026 threads did, so the patch review stays focused.

## Sending

Mail goes out with [git send-email](https://git-scm.com/docs/git-send-email), packaged on Fedora as `git-email`, through `smtp.gmail.com` on port 587 with a Gmail app password. The app password is kept in a mode-600 Git credential store file used only for that SMTP host. Git's `sendemail.confirm` is `never`, so a send command transmits immediately; the approval below happens before the command runs. An app password also grants IMAP access to the whole mailbox, so it is revoked from the Google account's app-password page when no longer needed.

Send each message only after the author explicitly approves that exact message:

```sh
git send-email --to zsh-workers@zsh.org --suppress-cc=all MESSAGE.patch
```

After it appears in the archive, record its `X-Seq` number and link in the matching entry of [UPSTREAM-ZSH-BUGS.md](UPSTREAM-ZSH-BUGS.md).
