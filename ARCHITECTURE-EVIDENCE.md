# Zsh fork and launcher architecture evidence

The login-shell failure is evidence for removing mandatory per-user activation state from shell startup. It also strengthens the case for evaluating a native Wsh entrypoint, but does not establish that a deeper Zsh fork is necessary: an installation-owned default bundle could remove the same dependency while retaining a launcher. Earlier experiments support targeted native patches where Zsh owns the faulty behavior, and show several cases where ordinary Zsh configuration or a small adapter already solves the problem.

This is a living decision record, reviewed on 2026-09-08. It records findings and candidate directions; production architecture remains unchanged. Linked reports retain the source revisions, bundle identities, fixtures, commands, raw results, and verification boundaries behind each observation.

The selected destination and ordered implementation/testing stages are in [NATIVE-IMPLEMENTATION-PLAN.md](NATIVE-IMPLEMENTATION-PLAN.md): native startup and tools, system-package updates, and an all-C implementation as the preferred hypothesis for remaining components. The Rust runtime, current plugins, and helper-process boundary remain comparison baselines. Prompt rendering and shell lifecycle stay local regardless of the selected implementation.

## Separate packaging, entrypoint, and engine decisions

Wsh already distributes a pinned Zsh with two narrow source patches. The practical choice is how much additional responsibility to move into that native executable, and which launcher or startup code that would let us delete.

| Decision | Alternatives | Question to resolve |
|---|---|---|
| Required installation state | Mandatory per-user activation record, or an installation-owned default with optional user selection | Can a fresh account start its shell without first running Wsh setup? |
| Shell entrypoint | Rust launcher that executes Zsh, or a Wsh entrypoint in the bundled Zsh executable | Which approach preserves native invocation and startup semantics with less duplicated code? |
| Native patch scope | Focused upstreamable corrections, startup integration, or broader engine changes | Which reproduced failures or costs require changing native code? |
| Shared services and management | External Rust runtime and manager, or work moved into Zsh | Does an identified process or protocol boundary cause enough cost or complexity to justify moving it? |

A fork that still requires the same activation record would retain the login failure. A launcher with a usable installation-owned default could avoid it. Neither approach survives removal of its required executable and libraries merely by changing the entrypoint design.

## Native entrypoint prototype supports simpler startup ownership

The [host prototype](benchmarks/native-entrypoint-2026-09-08/report.md) now compares both approaches. Both start without user activation state. The native entrypoint restores raw Zsh startup-file evaluation context and initial status, passes the existing shell contracts and upstream suite, and removes seven net lines from the compared startup implementation. It improves paired median readiness by 0.926 ms with an existing prompt and 0.810 ms with the minimal theme; both fixed regression gates pass.

The result favors native startup ownership as the next integration direction, with a modest code reduction. Management and exact foreground commands still use the unchanged manager. The native executable does not yet dispatch the public management CLI, so that interface and the installation/update contract remain design work before adoption. Tracking upstream already carries maintenance work; this adds a focused startup patch whose future rebase-conflict cost has not been measured.

The external Fedora account incident establishes the severity of a failed account shell. The fresh-account reproduction establishes one concrete failure mechanism; it does not prove that the original account lost its activation state. The recovery tests exercise real execve and PTY behavior, not a complete GDM/PAM login or reboot. Recovery remains development work after v0.3.1.

Duplicate user-selected renderers need explicit ownership regardless of the executable language. A fork does not itself reveal which theme or plugin behavior the user intends to retain.

## Candidate direction and comparison criteria

The preferred end state is a complete installed Wsh that can start its matching Zsh without per-user activation data. User selection can remain an optional override. Invalid selection should produce a diagnostic and leave a usable Zsh path, subject to the installation itself remaining intact. The current Bash safeguard provides emergency access, but command strings interpreted by Bash can have different semantics; a matching Zsh default would avoid that language change.

Native startup ownership, one user-facing executable for shell and tool invocation, and system-package ownership of installation and updates are the selected direction following the user's decisions on 2026-09-08. Implement native diagnostics first, then complete startup and packaged login before the larger C runtime and component comparisons. The [implementation plan](NATIVE-IMPLEMENTATION-PLAN.md) leaves language, format, and process-boundary details open to measured replacement. The installation-owned launcher remains a measured comparison.

| Candidate | Concrete benefit | Unproven work or cost |
|---|---|---|
| Current launcher with emergency Bash recovery | Tested access recovery for supported pre-exec failures | Requires Bash and changes command-language semantics during recovery; does not remove activation dependence from normal Zsh startup |
| Launcher with an installation-owned default Zsh bundle | Starts the same shell language without user selection in the host prototype | Must establish relocatable lookup, installation lifetime, update behavior, and fresh-account access |
| Minimal native Wsh entrypoint and startup integration | Uses Zsh argument parsing and removes manual startup-file sourcing in the host prototype | Shows seven net lines removed and passing host contracts; still needs a management-command interface, installation migration, portability, and reproducibility validation |
| Broader Zsh fork or rewritten editor/completion engine | Could change internal behavior beyond existing extension points | No retained experiment yet demonstrates a requirement for this scope; maintenance and compatibility costs need a specific benefit |

A login-capable candidate must pass empty-home startup, absent and corrupt optional selection, permission-denied selection, changed HOME/XDG environments, native login and noninteractive invocation, exact argument bytes, and command exit-status checks. It must preserve startup-file order, supported options, plugin and completion behavior, job control, and terminal reporting. Test missing required installation files separately so the claimed recovery boundary remains explicit.

Compare startup using the same Zsh build, enabled features, fixtures, and instrumentation, with readiness measured after editor initialization. The [readiness correction](benchmarks/profile-readiness-2026-09-05/report.md) and [matched profiling revalidation](benchmarks/profile-order-investigation-2026-09-06/report.md) explain why historical visible-prompt timings and unmatched binaries cannot establish a new performance claim. Follow the normal correctness, portability, reproducibility, and retained-evidence gates in [DEVELOPMENT.md](DEVELOPMENT.md).

## Updating this record

Cross-shell sharing is a separate potential experiment from the selected native entrypoint. Today each Wsh shell with a selected Wsh theme starts its own Rust runtime; regular Zsh and existing-prompt mode do not. A per-user Git service could coalesce duplicate work across panes while keeping rendering and shell lifecycle local. The [feature admission trigger](FEATURES.md) requires measured aggregate cost and comparison with simpler per-session improvements before introducing that service. The local helper-versus-in-process comparison in the native implementation plan does not require sharing across shells.

Add a finding when a reproducer identifies a boundary failure, a smaller counterfactual succeeds or fails, or a native prototype demonstrates concrete simplification. Record the affected layer, linked evidence, smallest alternative, and what the result leaves unresolved. Replace invalidated recommendations rather than accumulating contradictory plans. A passing compatibility experiment with no worthwhile optimization supports retaining the working boundary.
