# Official release and local build policy

Only an immutable GitHub Release in `wakamex/wsh` is an official `wsh` release. Every bundle produced by a local checkout, pull request, ordinary branch workflow, or manual build remains a development bundle. A local build can reproduce and verify an official asset byte-for-byte, but matching bytes do not make the local copy an independently published official release.

## One release publishes complete target bundles and matching tools

Each target bundle is one canonical archive containing the exact Zsh binary and modules, matching `wsh` runtime, integration adapter, schemas, and bundled theme definitions. Individual payload files are never release assets that the manager can mix into an installed bundle. The same release also publishes the matching compact launcher, separate install helper, release-specific bootstrap, and byte-identical `wsh-install.sh` alias because the native tools cannot live inside the bundle they must select or recover. Changing Zsh, Rust code, a trusted adapter, a schema, a theme, either release tool, the compiler, a linked dependency, or build flags creates a new complete candidate and reruns every gate.

The first target is `x86_64-unknown-linux-gnu` with glibc 2.28 as its tested compatibility floor. The Rocky Linux 8.10 floor experiment built the complete bundle from source and passed the upstream Zsh suite, Rust suite, relocated-bundle verification, real provider request, interactive PTY lifecycle test, dynamic-dependency comparison, and maximum-symbol check without importing a symbol newer than `GLIBC_2.28`. The exact bundle was also rejected by the glibc 2.27 loader with `GLIBC_2.28 not found`, confirming the artifact boundary. The retained result is in [`benchmarks/portability-glibc-2.28-2026-09-02.md`](benchmarks/portability-glibc-2.28-2026-09-02.md).

The runtime contract consists of the tested floor environment, glibc 2.28 or newer, and the system-supplied ELF library sonames recorded for the bundle payload and separate release tools. Compatibility claims for another distribution require execution there. The canonical build uses the public Wsh builder image by immutable OCI digest, with its package lock and recipe digest checked locally before use. Moving the floor, builder image, or dynamic-library boundary requires a recorded compatibility reason and a complete rerun.

## Reproducibility compares two isolated builds

The release workflow starts twice from the same pinned source commit, upstream Zsh source lock and snapshot, upstream signature when the source is a signed release, dependency lockfile, Rust toolchain, target, builder image digest, build recipe, environment, locale, timezone, archive ordering, timestamps, ownership, and compression parameters. The jobs use separate clean workers and do not exchange build directories or compiler caches. Each job emits the canonical archive digest, bundle manifest digest, file table, toolchain identities, test results, and build log.

The development implementation supplies the local form of this gate. Its Rocky lock records the complete installed package set with NEVRA, architecture, RPM header SHA-256, payload digest algorithm, and payload digest. Its Rust lock records exact compiler versions, required rustup components, and the digest of every file declared by those component manifests. A package that no longer resolves to the lock causes a failure; the repository does not currently retain an offline RPM archive. The canonical archive uses sorted GNU tar entries, the source commit timestamp, normalized ownership and modes, and fixed single-threaded xz parameters.

The retained [`947d812` local comparison](benchmarks/reproducible-build-947d812-2026-09-02/report.md) passed this byte-identity gate with archive SHA-256 `5b679a0d99867ee38af7acd8bdd3c9cfe75a3612d555aeaeb5c9f3282811c447`. It used two isolated worktrees on one host, so the official workflow must still reproduce the result in its clean jobs and emit the required provenance.

Publication is blocked unless the two canonical archives, manifests, launchers, installers, and generated bootstrap scripts match byte-for-byte. Agreement detects undeclared state and nondeterminism between those executions. It does not establish two independent trust domains when both jobs run on GitHub infrastructure. A later second-provider builder is justified if the project wants that stronger claim.

The agreed release outputs are subject to GitHub build-provenance attestations tied to the release workflow, repository, commit, and artifact digest. The project also publishes the two build records so a third party can rerun the same recipe. GitHub documents both [artifact attestations](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations) and [offline attestation verification](https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations).

## An annotated tag deliberately starts automatic publication

The maintainer prepares `release-notes/vMAJOR.MINOR.PATCH.md`, runs `./build/check-release-preflight.zsh vMAJOR.MINOR.PATCH`, and pushes the annotated tag only after remote `main` points to the intended commit and its `release-eligible / validate` check succeeds. The preflight also requires a matching workspace version and confirms that the tag and GitHub Release do not already exist. The tag is the human release authorization for the committed notes and artifacts. The publisher independently reruns validation, confirms that the tag matches the workspace version and an exact commit on `main`, requires the successful main-push eligibility workflow for that commit, and rejects a missing, empty, or symbolic-link notes file.

Two fresh release jobs build the tag through the canonical glibc 2.28 path without shared build or compiler caches. Publication is blocked unless their archives, manifests, launchers, installers, and release-specific bootstrap scripts match byte-for-byte. The workflow publishes one matching archive, its manifest, matching release tools, versioned bootstrap, byte-identical stable bootstrap alias, both build records, checksums, and the offline Sigstore bundle produced for those staged files. It uses the versioned notes file verbatim instead of relying on GitHub's pull-request-oriented generated notes. It does not accept manually selected, locally rebuilt, or separately uploaded assets. A downstream job verifies the exact notes, immutable Release metadata, and complete published asset set, then performs an anonymous installation and first-prompt launch from the exact public versioned URL. It checks the stable installer alias only while that tag is GitHub's latest release, so an older release remains independently verifiable. A failed downstream verification can be rerun without recreating the immutable Release.

If the publication job is rerun after GitHub has made the Release immutable, the archive, manifest, launcher, installer, versioned bootstrap, and stable bootstrap alias must match the new canonical builds byte-for-byte. The workflow separately validates the original published checksums, source-bound build records, offline build provenance, notes, metadata, and exact asset names. Run identifiers and attestation invocation identities remain part of the original evidence instead of being expected to reproduce. Downstream verification receives that validated immutable asset set.

GitHub release immutability must be enabled before a release tag is pushed. `gh release create` internally assembles the assets as a draft and publishes only after the uploads complete. Immutability takes effect when GitHub publishes the release, after which the workflow verifies the release attestation and every local asset against the published release.

GitHub immutable releases lock the tag and assets and automatically produce a signed release attestation covering the tag, commit, and assets. GitHub documents these properties in [Immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases) and exposes release and local-asset verification through `gh release verify` and `gh release verify-asset` in [Verifying the integrity of a release](https://docs.github.com/en/code-security/how-tos/secure-your-supply-chain/secure-your-dependencies/verify-release-integrity).

The release workflow verifies GitHub's immutable release attestation after publication. The native installer separately verifies the downloaded archive's workflow build provenance against the numeric `wakamex/wsh` repository identity, exact tag ref, exact source commit, exact `.github/workflows/publish.yml` signer and revision, and artifact digest. It then verifies the bundle manifest and every installed file and rejects an older version unless the user explicitly requests a downgrade. Missing, unsupported, or invalid verification material fails closed. The current native verifier does not yet implement GitHub's distinct TSA-backed release-attestation format, so client-side verification of that second attestation is deferred rather than claimed. A custom project signing hierarchy remains deferred unless GitHub build provenance proves unsuitable or another release channel is admitted.

## Activation and rollback remain local atomic operations

The release-specific bootstrap is the install protocol. It embeds the exact tag, source commit, asset names, immutable GitHub Release URLs, and launcher and installer SHA-256 digests produced by the agreed build. It downloads the archive, offline provenance bundle, launcher, and installer into a private temporary directory and verifies both downloaded native tools before executing or installing either. It validates both selected tool destinations before mutation, rejects symbolic links and non-regular files, stages each replacement in its destination filesystem, and atomically replaces an older regular tool. The bootstrap is included in the two-build comparison, checksum list, and workflow build-provenance attestation. The publisher also exposes the same bytes as `wsh-install.sh`, allowing GitHub's `/releases/latest/download/` path to select the current immutable release without maintaining a script on a mutable branch.

Build-provenance verification happens once against the downloaded archive before extraction. Extraction and payload verification happen in a new private directory beneath the installation root. After the candidate passes fixed Zsh and runtime smoke tests, the installer moves the complete content-addressed bundle into place and one atomically replaced state record selects it, retains the previous selection, and records the bounded metadata required for startup. An interrupted or rejected install leaves the old state record intact. Ordinary startup reads only that record and replaces the launcher with Zsh; it does not parse attestations, archives, or the complete manifest. Rollback rehashes and selects the previous bundle without network access or a working active Zsh or runtime.

The manager never mutates an installed bundle and never updates one component within it. Shell startup performs no update check, network request, or update mutation. `wsh update --check` resolves GitHub's current immutable release without mutation. `wsh update --to vMAJOR.MINOR.PATCH` runs the exact release bootstrap, while bare `wsh update` resolves the current release and runs its exact bootstrap only when newer. Both paths compare against the active verified release, reject downgrades before download, and reuse the bootstrap rather than introducing another installation protocol. `wsh bundle activate` and `wsh bundle rollback` remain separate local operations.

## Release gates

An official GitHub Release requires all of the following:

1. The exact source commit and tag are fixed.
2. The upstream Zsh source mode, canonical location, revision, tree, snapshot digest, maintainer signature when present, dependency lockfile, toolchain, builder image, and build recipe are pinned.
3. Rust tests, Zsh upstream tests, theme-schema tests, provider fixtures, adversarial protocol tests, PTY lifecycle tests, tamper tests, and rollback tests pass.
4. The complete bundle runs in the documented floor environment, imports no glibc symbol above the floor, and exactly records its system-supplied dynamic-library boundary.
5. The retained benchmark passes semantic, process-count, optional-lock, repaint, first-editable, settled-latency, tracing-overhead, and memory gates.
6. Two isolated canonical builds produce the same archive, manifest, native-tool, and bootstrap bytes.
7. Build-provenance attestations cover the agreed assets and workflow identity, their offline Sigstore bundle is published, and the native verifier accepts the archive only under the exact release policy.
8. The automated publisher supplies the complete asset set and both build records before GitHub publishes the release and makes it immutable.
9. Release and asset verification succeeds after publication.

`v0.1.3` permits an exact release bootstrap to replace older regular launcher and installer files after the downloaded replacements pass their embedded digests and adds explicit check, latest, and exact-version update commands. Its [public update result](benchmarks/public-update-v0.1.3-2026-09-03.md) verifies the real v0.1.1 to v0.1.3 replacement, offline rollback, and subsequent update through the installed command. `v0.1.2` suppresses the internal runtime job announcement while preserving a separate runtime process group, interactive job control, and prompt interrupt handling, but its bootstrap cannot update an existing release because it requires the old native tools to equal the new digests. `v0.1.1` is the first installable official binary release to pass all nine gates and the separate public download-to-prompt experiment. Immutable `v0.1.0` passed the original publication workflow but failed its first public install before activation, which added relocated candidate startup to gate 3 for subsequent releases.
